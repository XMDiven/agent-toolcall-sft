# 项目讲述要点

把这个项目讲清楚需要回答六个问题。每个问题下面是**结论**、**证据**和**别人最可能追问的点**。

所有数字取自 `docs/evidence/metrics_traceability.md`，对外表述前先过一遍那份文档第 4 节。

---

## 一句话版本

> 在 6GB 显存的笔记本上把 Qwen3-1.7B 微调成客服场景的工具路由模型，行为准确率从 36.2% 提到 95.4%（95% CI [+0.5460, +0.6360]），危险写工具误调用率从 17.78% 降到 1.11%。
>
> 但这个项目真正想证明的不是模型变强了，是**这些数字经得起别人复算**。

如果只能说三十秒，说到这里停。对方感兴趣自然会追问，那时再展开下面任意一条。

---

## 一、为什么在已有 RAG 应用项目之外，还要单独做微调

**结论：** 因为同一能力的第二份实现，边际价值接近零。开工前先做了一次裁剪。

**证据：**

| 保留（平台没有的） | 砍掉（平台已有的） |
| --- | --- |
| 4-bit QLoRA 训练本身 | Pydantic 契约（照搬已验证的判别联合模式） |
| 冻结基线 + 防泄漏切分 | Docker 与 CI（复制配置，不作里程碑） |
| 危险写工具误调用率的量化 | **只读 RAG 检索链路（完全不重复实现）** |
| 微调模型作为可插拔 router 接入 | |

**两个项目的分工：** 应用层回答"检索到的内容够不够好"，模型层回答"该不该调工具、调哪个、参数对不对"。

**方法论上还互补：** 平台的评测用 LLM-as-Judge，依赖裁判模型打分；本项目用冻结基线 + 配对统计检验，结论可复算、不依赖任何裁判模型。两者盲区不同。

**可能被追问：**

> "那你这个项目的技术含量是不是就只有 QLoRA？"

不是。QLoRA 本身网上教程一抓一把，**真正难的是让结果可信**——冻结基线、防泄漏切分、配对检验、修订纪律，这些占了项目大部分投入。见第四点。

---

## 二、工具契约怎么和已有平台对齐

**结论：** 三个知识工具的名称与必填参数签名与平台 `tools/registry.py` 完全一致，**无需名称映射即可被平台派发**；本项目额外收紧校验。

**证据：**

```
retrieval_tool(question) · summary_tool(text) · question_decompose_tool(question)
两边逐一比对一致，回归测试 test_retrieval_tool_matches_platform_signature 守着
```

七个工具用 Pydantic 判别联合，`extra="forbid"` fail-closed。**最值得讲的一处设计：**

```python
class CreateRefundRequestArgs(StrictModel):
    confirmed: Literal[True]
```

`confirmed` 的类型是 `Literal[True]`——**"未确认的退款"在类型层面无法表达**，不是靠运行时 if 判断。

**可能被追问：**

> "类型层面挡住了，那为什么还会有 1.11% 的误调用？"

好问题，而且我们真的遇到了：模型绕过它的方式是**替用户填 `confirmed: true`**。类型系统能保证"结构上不可能出现未确认的退款调用"，但保证不了"模型不会自己声称用户确认了"。这个案例写在 README 正文里。

## 三、数据怎么防泄漏

**结论：** 按 `template_key` 分组切分，六道门禁全过。测试集里每一个模板在训练集中都没出现过。

**证据：**

```
内容哈希 · 规范化文本哈希 · 完整记录 fingerprint
模板键交集 · 参数化句式交集 · 4-gram 近重复
leakage_clean: true
```

**最值得讲的是第五道门禁。** 前四道抓不到这种情况：

```
训练集  不是我想要的那种，订单 ORD-751598，确认要退款。
测试集  不是我想要的那种，订单 ORD-480790，确认要退款。
```

原文哈希不同，所以"检查通过"。但把 `ORD-\d{6}` 抹成 `ORD-NNNNNN` 之后哈希撞上——**这就是同一道题换了个随机数**。

**这道门禁不是一开始就有的。** 它是在审计 v1 数据时发现 30 个句式、90 条记录跨界之后补上的，补完 v1 的证据整轮作废重来。

**可能被追问：**

> "怎么证明测试集真的没泄漏？"

`data/manifests/split_v2.json` 里有结论，而且有测试断言"仓库里的 manifest 必须等于当前代码的产物"——改了门禁却忘了重签，测试立刻变红。数据本身用固定种子生成，我在 macOS/ARM 上重新生成过一次，manifest 哈希与 Linux/x86_64 上**逐字节相同**。

## 四、为什么要冻结基线

**结论：** 因为"微调后 95.4%"这个数字，脱离对照什么都不是。而对照必须在训练之前测完并锁死。

**证据：** 冻结评测在开始和结束时各拍一次输入快照（git commit、工作区状态、manifest 哈希、模型权重逐文件哈希），**两次不一致就拒绝发布结果**。

**最值得讲的是它真的拦下过一次。**

一次 500 条的评测跑完了 26 分钟推理，最后一步报错：

```
RuntimeError: evaluation inputs changed during the run; refusing to publish
```

原因是我在推理进行中往仓库里拷了两个 markdown 文件，工作区变脏。系统分不清我改的是无害的文档还是关键的打分代码——**所以它宁可丢弃整轮推理，也不发布一份来源说不清的数字**。

**可能被追问：**

> "为什么不训练完再测基线？反正模型没变。"

因为人会不自觉地挑对自己有利的配置。先测、测完锁死，是把这个可能性从流程里移除，而不是靠自律。

## 五、6GB 显存怎么控制

**结论：** 训练用 4-bit，评测和推理用 fp16。这个分工是刻意的。

**证据：**

```
训练     4-bit NF4 + double quant，batch 1 × 梯度累积 16，seq 1024
         gradient checkpointing，峰值显存 4.11 / 6.00 GiB，250 步 52 分钟
可训练   17,432,576 / 1,033,364,480 = 1.687%
Adapter  66.56 MiB
```

**smoke test 抓到过一个典型问题：** 16 步训练全部跑完，最后评测时 OOM。

```
torch.OutOfMemoryError: Tried to allocate 3.25 GiB
```

原因是没设 `per_device_eval_batch_size`，库默认是 8。算一下：`8 × 718 token × 151936 词表 × 4 字节 ≈ 3.25 GiB`，和报错数字完全吻合。

**如果留到全量训练，会在跑了两小时之后、第一次评测时爆掉。** 现在配置里那一行写着为什么不能省。

**可能被追问：**

> "为什么评测不也用 4-bit？"

因为 4-bit 只是训练时的省显存手段，评测要的是模型的真实行为。这个分工还带来一个好处：Adapter 可以直接合并回 fp16 基座，产出一个不依赖 PEFT 的独立模型——**我把它部署到了 M4 Mac 上，跑同一批 500 条，500/500 判定一致、498/500 逐字节一致**。

## 六、结果和边界

**结论：** 四项验收全部通过，但有三条限定必须和数字一起说。

**结果：**

```
行为准确率     0.3620 → 0.9540   CI [+0.5460, +0.6360]
危险写误调用   17.78% → 1.11%    CI [−0.2222, −0.1167]
JSON 合法率    100.00%
Schema 合法率  87.00% → 99.60%
清单外调用率   0.20% → 0.00%
```

**三条必须同时说的限定：**

**1. 提升的主体是"学会了输出契约"，不是"更会选工具"。**

基座模型在自己的原生工具格式下，工具名选对率就有 92.38%；在本项目自定义的四决策 JSON 契约下只有 48.88%。差距来自格式不合规。所以这个提升准确的含义是：模型学会了我们的契约，并在此前提下保持了原有的路由能力。

**2. 中途一次修订带来了 2 条危险写误调用。**

序列化格式的修订让整体指标上升，但决策边界随之右移（`tool_call` +24 条、`clarify` −8 条），出现 2 条本该追问却直接执行退款的案例。仍在 2% 阈值内、统计上不显著，但**正是这个项目要防的两种行为**。

**3. 置信区间偏窄约 1.6 倍。**

500 条测试记录来自 190 个 `template_key`，bootstrap 的独立性假设不成立。

**可能被追问：**

> "那 2 条危险误调用你为什么不修掉？"

因为修订机会只有一次，已经用掉了。**看到测试集结果之后再回头调参重训，会毁掉这个项目最值钱的东西**——那时报出来的就不再是"冻结测试集上的结果"。这条规则是项目开始时定的，不是事后找的理由。

## 三个最值得主动讲的时刻

数字会被质疑，这些不会。

**一、撤回过一整轮已经产出的证据。**

数据审计和基线报告都跑完了、写完了，但后来发现打分器本身有 bug（多调用没判错、安全指标分母算错）。那一轮全部作废重来，作废的记录留在 git 历史里。

**二、写下过会被推翻的预测。**

改序列化格式之前，公开写下三条可证伪的预测，其中一条是"改格式不影响语义判断"。结果 18 条语义类失败里有 7 条变了——**预测错了，写进报告，并顺着这条线查出了决策边界位移和那 2 条危险写误调用**。

如果当时没写下预测，这个发现根本不会发生。

**三、发现自己把模型教坏了。**

微调后有 19 条输出是非法 JSON，而**基座模型这些题原本全对**。查下来是训练目标的序列化写法：`":"` 和 `:"` 在词表里是两个几乎一样的 token，模型选错一次整条 JSON 就废。基座模型天然写带空格的 JSON，从不碰这对 token。

**是我们选了一个"看起来干净"的格式，把一个本来安全的模型教到了不安全的写法上。**

教训写进了报告：选训练目标格式时，先用目标模型的分词器切一遍看有没有易混 token。这个检查不到一分钟，我到错误分析阶段才做。

## 不要这样说

完整清单见 `docs/evidence/metrics_traceability.md` 第 4 节。最容易踩的三条：

```
✗ "准确率提升 59 个百分点，危险写误调用归零"
   归零是 v1，0.9540 是 v2，拼在一起描述的模型不存在

✗ "微调让 1.7B 的工具路由能力翻倍"
   提升主体是契约遵循；基座在原生格式下已有 92.38%

✗ "95% CI [+0.5460, +0.6360]"（不加限定）
   有效样本量接近 190 个模板而非 500 条记录，区间偏窄
```
