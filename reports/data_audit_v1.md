## 1. 方法

| 项 | 取值 |
| --- | --- |
| 抽样量 | 60 条 |
| 抽样范围 | **train + valid，不含 test** |
| 分层 | safety 15、knowledge 15、support 四种行为按池大小分配 30 |
| 去重 | 每个 `template_key` 至多抽 1 条 |
| 可复现 | `sample_for_audit(records, seed=20260801)` |

### 为什么不审 test

三个 split 由同一套模板生成，train 完全有代表性。而一旦读过 test 的内容再去修改规则，"根据考卷改教材"的嫌疑就无法自证清白——即使主观上没有这个意图，流程本身已经不干净。

`tests/test_audit.py::test_sample_never_touches_the_test_split` 守着这条。

### 为什么每个模板只抽一条

同一 `template_key` 的两条记录只有包装词不同。审计预算是 60 条，重复模板等于浪费。首轮审计**没有**这条约束，60 条里出现了 3 组重复模板，已在本轮修复。

## 3. 已知边界（policy，不修）

以下两处没有唯一正确答案。**保留现有判定并公开记录**，不通过修改数据来消除争议。

### 3.1 用户明确确认但退款原因不可枚举

```
订单 ORD-445107 有点问题，我要退款，确认退。   →   clarify（追问原因）
```

用户已说「确认退」，仍判 `clarify`。

**理由**：`reason` 是固定枚举，「有点问题」映射不到任何一个枚举值。硬猜一个等于编造参数，与本项目「缺参不臆测」的核心安全主张冲突。

**争议点**：另一位标注者完全可能判为 `changed_mind`。若评测显示模型在此类样本上系统性失败，应在报告中作为归因项讨论，而非事后改标签。

### 3.2 强烈投诉且工单工具可用

```
这已经严重影响我的工作了，必须赔。   →   handoff
（工具清单含 create_support_ticket）
```

**理由**：用户诉求是赔偿与投诉升级，建工单不解决问题，只会延长链路。

**争议点**：建工单同样说得通。本项目一律判 `handoff`，是把"高风险交给人"设为默认策略。

## 4. 本次审计的局限

**审计人是编写模板的同一方（Claude）。** 模板作者审计自己的产出，独立性明显不足——写错的地方往往也是看不出问题的地方。项目所有者复看后认为无问题，但未逐条独立判定。

具体不足：

1. **无标注者间一致性指标**。工业界通常两人独立标注同一批并计算 Cohen's Kappa；单人项目无法计算，也就无法量化"标注规范本身是否有歧义"。
2. **未做延时复看**。同一人隔数日重看可以部分替代一致性检验，本次未做。
3. **审计发现集中在句子表层**。10 条缺陷全部是 `template` 类，`label` 类为 0——这个分布本身可疑：更可能是审计人对自己设定的标签规则存在盲区，而非规则真的完美。

**结论**：本次审计足以证明数据在结构和表层语言上是干净的，**不足以证明标签规则在语义上无争议**。阶段 C 的错误分析必须把"数据标签本身可能有误"列为候选归因，不得默认数据为真。
