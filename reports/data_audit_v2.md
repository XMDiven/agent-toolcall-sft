## 3. 主要发现

### 3.1 `refund_missing_confirmation` 的措辞与标签意图错位（3 条，影响评测口径）

样本第 37、38、39 条。该族的设计意图是"用户有退款意向但未明确确认"，标准答案为 `clarify`，话术是"退款提交后不可撤销，请确认是否现在为该订单发起退款"。

但句子模板用的是"我先了解下退款政策"和"退款流程麻烦说一下"——**这两种措辞表达的是询问政策，不是请求退款**。标准答案的话术因此假定了一个句子没有表达的意图。

影响不止于数据质量：第 37、39 条的可用工具清单中 `retrieval_tool` 在场。模型若输出 `retrieval_tool`（查退款政策）并非不合理，却会被判为错误。**这会在阶段 C 低估模型表现**，属于评测口径问题而非模型问题。

阶段 C 的错误分析必须把这三个模板族列为候选归因，不得默认数据为真。

### 3.2 「麻烦」重复暴露表层检查盲区（2 条）

样本第 49 条"麻烦问一下，麻烦看看订单号 ORD-831249，发货了吗？"、第 58 条"麻烦开个工单跟进。麻烦了。"——包装词与模板正文选用了同一个词。

值得记录的不是这两句本身，而是它说明"同词组紧邻重复"这项表层正则**只能捕获紧邻重复**，中间隔一个短语就漏掉。旧报告据此声称的"0 处"因此是该正则口径下的 0，不是语言质量的 0。

### 3.3 知识域"对比"与"单点"的边界很细（2 条）

样本第 4 条"新用户券和会员券能同时用吗"标 `question_decompose_tool`，第 8 条"优惠券怎么叠加使用"标 `retrieval_tool`。两条问的都是优惠叠加规则，区分依据是**是否点名了两个具名对象**。

规则可自洽，但边界细到另一位标注者可能给出不同判断。第 4 条的清单中两个工具同时在场，模型选 `retrieval_tool` 会被判错。

### 3.4 `strong_complaint` 族内升级强度不均（1 条）

样本第 28 条"你们的解释根本站不住脚"只表达不满，没有索赔、升级或诉讼信号，升级强度明显弱于同族第 27、29、30 条。标 `handoff` 可辩护但不唯一。

## 5. 语料多样性与有效样本量

`template_key` 计数取自两份 manifest，可直接复算：

| 指标 | v1 | v2 |
| --- | ---: | ---: |
| 全语料不同 `template_key` | 454 | **793** |
| 训练集 | 304 | **467** |
| 验证集 | 59 | **136** |
| 测试集 | 91 | **190** |
| 测试集内容复用次数 | 5.49 | **2.63** |

**为什么这件事影响结论**：bootstrap 置信区间假设样本独立。同一 `template_key` 生成的多条记录高度相关，有效样本量接近 `template_key` 数而非记录数。按 n=500 计算的区间实际对应 n≈190，**宽度被低估约 1.6 倍**（v1 为 n≈91，低估约 2.3 倍）。

**阶段 C 报告置信区间时必须同时给出 `template_key` 计数，不得只写 n=500。**

## 6. 已知边界（不修，公开记录）

### 6.1 用户明确确认但退款原因不可枚举

```
ORD-687750 这单跟宣传的差挺多，确认退款。   →   clarify（追问原因）
```

`reason` 是固定枚举，"跟宣传的差挺多"映射不到任何值，臆造即违反"缺参不猜"的核心主张。但另一位标注者完全可能判为 `wrong_item` 或 `quality_issue`。

### 6.2 能力问答与工单的边界

`capability_question:你可以帮我催发货吗？` 标为 `direct_answer`，但其标准答案本身提到"需要通过工单转交"。

### 6.3 知识域与退款资格的语义邻近（有意设计）

`kb_lookup` 中有 **11 个** `template_key` 是退款相关政策问题（退货政策、拆封后能否退货、生鲜能否退、赠品单退、退款到账时长、促销期规则、定制商品、秒杀商品、原路返回、退货地址、会员费）。它们与 `check_refund_eligibility` 语义邻近，属于**有意放置的困难负样本**：考察模型能否区分"问政策"与"查具体订单的退款资格"。

> 旧报告写的是 4 条，实测为 11 个 `template_key`，已更正。

### 6.4 抱怨文本到 `reason` 的映射泛化覆盖极薄

三个退款族共用同一套抱怨素材。实测：

```
train + valid 中出现的 (抱怨 → reason) 映射：49 个
test 中出现的映射：                        22 个
test 中训练未见过的映射：                   1 个
```

**测试集里只有 1 个映射是模型没在训练中见过的。** 这意味着参数 exact match 几乎完全在衡量查表记忆，而非抱怨语义到枚举值的泛化能力。

阶段 C 报告参数准确率时必须写明这一点，不得把它当作泛化能力的证据。

> 旧报告写的是 3 个，实测为 1 个，已更正。覆盖比原先记录的更薄。

### 6.5 旧报告中已不存在的边界（已删除）

旧报告 4.2 记录了两条工单/转人工边界（`同一笔订单被重复扣款`、`账号被提示异常无法下单`）。实测这两个 `template_key` 在当前 v2 语料中**不存在**，该条已删除。

## 7. 未修复项与理由

第 2 节的 4 条 `template` 瑕疵**本轮未修**。

- **性质**：均为表层措辞（同词重复、指代略绕），标签、参数、工具清单与安全标签全部正确；
- **代价**：改模板意味着整个语料重新生成，`data/manifests/split_v2.json` 的三个指纹全部作废，本次 60 条审计需要重做；
- **对评测的影响**：这类瑕疵在 train 与 test 中同样存在，不会使基线与微调模型的比较产生偏向；本项目评的是工具路由，不是语言流畅度。

**结论：记录而不修复。** 该决定已于 2026-08-03 经项目所有者复核确认。若后续认为语言质量属于交付标准的一部分，这个决定仍可推翻——那需要重新生成语料并重跑本节之前的全部步骤。

第 3.1 节的措辞错位是更值得考虑修复的一项，因为它影响评测口径而非仅仅是观感。同样未修，理由相同（代价是整轮重来），但它必须写进阶段 C 的归因候选。

## 8. 本次审计的局限

**审计由 Claude 执行，与模板编写方为同一方。** 模板作者审计自己的产出，独立性不足——写错的地方往往也是看不出问题的地方。

**部分缓解：** 2026-08-03，项目所有者复核了 11 条被标记为 `template` 或 `policy` 的样本（第 4、8、28、31、37、38、39、49、51、56、58 条），对每一条的结论表示同意，并确认第 7 节"记录而不修复"的处置。**其余 49 条判定为无问题的样本未经第二方复核**——而"看起来没问题"恰恰是盲区最可能藏身的地方，缓解仅限于已标记项。

具体不足：

1. **无标注者间一致性指标。** 单方审计无法计算 Cohen's Kappa，也就无法量化"标注规范本身是否有歧义"。
2. **未做延时复看。** 同一方隔数日重看可部分替代一致性检验，本次未做。
3. **自动检查只能证伪，不能证实。** 第 4 节全过，说明**没有已知类型的错误**，不说明标签在语义上无争议。
4. **姓名与地址无自动检查。** 第 4 节的 PII 扫描只覆盖手机号、邮箱、身份证这类有固定格式的标识符；姓名与地址依赖模板设计和本次逐条阅读，未经独立验证。
5. **`label` 类为 0 应当谨慎解读。** v1 审计同样出现"缺陷全落在 `template` 类、`label` 类为 0"的分布，ROADMAP 已记录这更可能反映审计盲区。本轮虽新增了 7 条 `policy`，但 `label` 仍为 0，同一质疑依然成立。

`reports/data_audit_v2_sheet.md` 的记录内容由 `render_audit_sheet()` 渲染，`结论` 与 `问题` 两行为审计人填写，因此工作表本身不是纯代码产物，不可仅凭命令复现。

## 9. 结论

**语料在结构、泄漏门禁、PII 和标签一致性上是干净的；语义争议性未经独立验证。**

60 条逐条审计发现 0 处标准答案错误、4 处表层措辞瑕疵、7 处场景边界争议。其中第 3.1 节的措辞错位与第 6.4 节的映射覆盖，会直接影响阶段 C 指标的解读方式，两者都必须写进阶段 C 报告。

阶段 C 的错误分析必须把"数据标签本身可能有误"列为候选归因，不得默认数据为真。
